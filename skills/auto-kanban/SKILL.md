# Auto-Kanban — capture-first board for agent workflows

A single durable board for bursty, multi-thread work between a human and an AI agent. It exists
because chat is a terrible database: the agent's context compresses and compacts as a session
runs, and anything that lives only in the transcript eventually decays into a summary of itself.

## Why This Is a Product Skill

Losing a thread isn't an engineering annoyance — it's how product intent leaks out of a build.
The constraint a stakeholder stated in passing, the alternative that was considered and rejected,
the half-formed idea that would have become the next feature: these are product decisions, and
chat memory silently drops them. A capture-first board makes the backlog a property of the
*system*, not of anyone's memory.

## Why this exists

Chat is linear and lossy. The agent compresses as it goes; context compaction preserves
*decisions* but strips *texture* — exact phrasings, half-formed asides, and above all the
**origin pointer** (which message an item came from). When a plan is later written from working
memory, anything that scrolled out of context is reconstructed from the compressed summary, not
the source. The result is conceptual entropy: constraints stated in passing vanish, rejected
alternatives resurface as fresh proposals, verbally-proposed config values never get named
settings, and the agent's own mid-turn discoveries (a bug found inside a tool call) are never
promoted because they didn't come from the user.

Two failure modes this system kills:

- **Capture failure** — a user request or flag is acknowledged in chat but never acted on, and
  falls out of context hours later.
- **Reconciliation failure** — stale context is carried forward (the agent nags the user about
  something they already did, or re-plans work that already shipped).

## The one rule: capture-first

Every user push AND every pre-planning idea the agent generates lands in the data file as a card
**in the same turn, before acting** — Inbox first, unprocessed. Nothing is allowed to live only
in the transcript. This includes the agent's own mid-turn finds (bugs, config knobs, risks
surfaced inside a tool result) — those are the most fragile, because nothing else will ever
re-raise them.

## Architecture — structured data as the source of truth

The board is **data**, not prose:

- **Source of truth:** `kanban.data.yaml` — structured cards, committed to the repo. Edit HERE.
  Must stay valid YAML before every commit.
- **Generated views:** a render script (`render_board.py` or equivalent) reads the YAML and
  emits `KANBAN.md` (human-readable markdown) and `board.html` (self-contained static page).
  Views are a pure function of the data — same input, byte-identical output. **Never hand-edit
  a view**; edit the YAML and re-render.
- **Staleness banner:** the data file carries `meta.last_reconciled`. The renderer compares it
  to repo activity signals (newest git tag, newest release notes file, or last commit date) and,
  if the repo has moved past the board, renders a loud STALE banner into every view and exits
  non-zero in `--check` mode. A board that must be *interrogated* for staleness is not a
  mechanism; a banner that appears by itself is.
- **History:** done cards age out of the active data file into `kanban.history.yaml` rather
  than bloating the board. Git history is the durable record.

## The ship gate — board currency as an output of releasing

Board reconciliation is typically the only step in a release ritual with no forcing function:
the deploy script refuses to run without tests and without release notes, but nothing refuses
without a board update — so it runs on willpower, and rots. Fix it by making the board update
an **output of shipping**, never a task beside it:

- The release script takes `--cards ID[,ID...]` and **refuses to deploy without it**, printing
  the current in-progress/review cards as candidates.
- Card IDs are validated *before* anything is pushed.
- After a successful push, the script writes `status: shipped` + the released version onto each
  card, updates `meta.last_reconciled`, and (if you keep a decision journal) emits the "why we
  shipped this" entry — so the status board and the decision trail cannot lag the release.
- An explicit `--no-cards` escape exists for pure-docs releases; it is logged, never silent.
- **Safety rule:** a failed board write must never abort a deploy that has already pushed.
  Write after the push succeeds; warn loudly on failure; never exit non-zero post-push. A stale
  board is strictly better than a half-released version.

## Card schema — the fields ARE the decay vectors

Fill Origin, Why, and Next even when terse. Each field maps to a specific context-loss failure
mode it kills:

| Field | Kills this leak |
|---|---|
| **Status / Thread** | which workstream — prevents cross-thread confusion |
| **Origin** (date + one-line gist of the originating push) | the origin pointer — full intent stays reconstructable after the message scrolls out of context |
| **Why** | rationale — a settled decision doesn't get re-litigated in a later session |
| **Constraints** | musts stated in passing ("must never auto-send", "keep the URL stable") that otherwise evaporate |
| **Parked-alts** (+ why rejected) | rejected options resurfacing as fresh proposals |
| **Knobs** | verbally-proposed configurables actually becoming named settings instead of magic numbers |
| **Next** | the single next action — a card is never inert; a title with no Next is a transcript line, not a card |
| **Refs** | planning doc / review record / commit — the card links to the durable artifacts |

Card template (as it appears in the YAML):

```yaml
- id: CARD-1
  title: One-line problem -> solution statement
  thread: area              # workstream
  status: inbox             # inbox / pre_planning / planned / in_progress /
                            # review / shipped / waiting_user / waiting_agent / parked
  approval: unreviewed      # unreviewed / implied / explicit / blocked
  origin:
    date: '2026-01-01'
    gist: one-line gist of the originating push
  why: rationale, so the decision is not re-litigated
  constraints: []
  parked_alts: []           # rejected options (+ why)
  knobs: []                 # named configurables this card introduces
  next: single next action
  refs: []                  # docs / commits / reviews
```

## Columns

`Inbox` (raw capture) → `Pre-planning` (idea being decomposed) → `Planned` (has acceptance
criteria) → `In progress` → `Review` → `Shipped` — plus three side lanes:

- `Waiting on user` — decisions or actions only the human can take.
- `Waiting on agent` — things the agent owes (a promised verification, a re-measurement).
  Track obligations on *both* sides; filing the agent's own debt under the user's lane hides it.
- `Parked` — deliberately deferred, always with a written revisit-trigger. Parked is not done:
  when a trigger fires, the card is READY, not forgotten.

## Cadence — bind updates to events, not to a clock

Clock-based cadences ("update the board every 30 minutes") rely on remembering a separate chore,
so they drift under load. Bind every board update to a checkpoint that already has to happen:

1. **Session start:** read the board; run the renderer's `--check`; if stale, reconcile against
   repo/live state *before* reporting status.
2. **On every push / mid-turn idea:** add or update a card the same turn, before acting.
3. **Pre-planning harvest:** before writing any planning doc, harvest the relevant cards —
   Origin / Why / Constraints / Parked-alts / Knobs flow straight into the plan. This is the
   anti-entropy handoff from chat to plan.
4. **Turn end:** reconcile — move cards between columns, write one-line dispositions, re-run
   the renderer so committed views match the data.
5. **Release:** the ship gate (above) marks cards shipped automatically.

## Anti-patterns

- A card with a title but no Origin/Next — that's a transcript line, not a card.
- Letting a mid-turn discovery stay in the tool output "because I'll remember it."
- Hand-editing a rendered view instead of editing the YAML and re-rendering — the data file is
  the source of truth; every view is a reflection, never the record.
- Creating a card without first sweeping existing cards, the backlog, and parked planning-doc
  deliverables for duplicates or adjacent work — a board that never merges becomes a list
  nobody reads, and duplicates split the evidence for one problem across two places.
- Silent moves: closing or moving a card without a one-line disposition. A card never just
  disappears.
- Treating a parked item as done. Parked means "revisit-trigger set" — check whether the
  trigger fired.
- Duplicating the decision journal's reasoning into the board, or the board's status into the
  journal. The board is WHAT / WHERE / NEXT; the journal is WHY. They compose.

## Product Lens

Before a card leaves Pre-planning, give it a parsimony verdict: is the problem sharp and real
(one falsifiable sentence), and is the fancy version worth its marginal risk over the simplest
version that captures most of the benefit? Record **BUILD / SIMPLIFY / PARK / DROP** on the
card. Reaching "good idea, not worth it now — park with a trigger" is a success of the gate,
not a failure.
